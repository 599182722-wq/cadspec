# 路线图

## 现在在哪

- **框架已完成**：Clause / Rule 分离、`cite` 强制回填、severity 归 `data/rules`、打印尺寸换算。
- **录入链路已通**：`scripts/ingest_pdf.py` 把规范 PDF 拆成条文 YAML，`scripts/ingest_html.py`
  把分章 HTML 拆成同一格式，一条命令处理一整本。
- **语料**：6 份 626 条 —— GB 55037 建筑防火（238 条）、GB 55031 民用建筑通用（142 条）、
  GB 55038 住宅项目（122 条）、GB 55019 无障碍（108 条）、GB/T 50001-2017 制图标准（11 条）、
  SJD-2016 深度规定（5 条）。六份的 `interpret` 全部写完，一条不落。
- **规则**：25 条。7 条判房间与门窗尺度，1 条查「缺画」（外轮廓有没有门），其余 17 条判图纸表达。
- **图面完整性**：7 项清单（房间名称、门窗类型、楼梯、尺寸、比例、剖切符号/指北针、标高），
  在报告末尾回答「这张图现在能被审到什么程度」，而不是只答「有没有问题」。
- **可读性体检**：`cadspec doctor` 11 项检查，分出「阻塞」与「建议」，直接给出这张图能跑哪几类
  检查（表达 / 几何 / 房间 / 尺寸）。起因是一张 7.5MB 的图——画满家具洁具，但图层叫 `123`、
  全图 0 个文字、墙是双线，工具在它上面只判出 2 条 error 和 0 个房间。**看起来很完整，可读性很低。**
- **样例**：`1.dxf` 作为回归基线。

框架到这一步已经能跑通「条文 → 规则 → 检查 → 定位到 entity」的整条链路，剩下的是填内容。

**几何识别的第一块地基已铺好**：`--level strict` 把墙线围成房间、从图内文字读出用途，
于是「卧室不应小于 5m²」这类条文第一次能自动判了。4 条规则落在 GB 55038 4.1 套内空间。

**门窗怎么分**：靠门扇开启弧。`1.dxf` 里 `ARC` 实体是 0，但门窗层有 11 条带 bulge 的
`LWPOLYLINE`，每条弧的半径恰好等于洞口宽度、且一端落在洞口上（那就是铰点）。这 11 处判门，
门窗层的 12 条多线判窗。更早的版本按多线样式名判，把 11 扇门全判成了窗——同一样式被
画图的人复用了，按名字判不只错，还错成「通过」。假阴性比判不出来危险。

**agent 接入**：`--level strict --format json` 的输出带房间（面积、净面积、短边、相邻关系）、
门窗（宽度、判定依据）和问题清单。房间之间的相邻关系由 Python 算（`Polygon.distance`
加洞口匹配），模型拿到的是「R7 与 R1 之间是一扇 800 的门」，不是一串坐标。
[`skills/cadspec/SKILL.md`](../skills/cadspec/SKILL.md) 写清了分工：**数由 Python 量，
语义由模型判，结论必须落到条号**。

**已知缺口**：只有 18 / 626（3%）条声明了 `checkable` 等级。真正难的不是声明，
是几何——DXF 里没有"房间""门""楼梯"，只有线和弧。房间已经能从墙线抠出来，
门只有洞口宽度、过道还没有定义、防火分区需要闭合边界，这些都还没做。
`--level strict` 对图纸有前提（MLINE 画墙、图层名约定），不满足时降级到 `basic`，
现在由 `cadspec doctor` 提前说明是哪一条不满足、要怎么改。

**不做双线墙识别**。真实图纸大量用两条平行线画墙，识别它要处理斜接、门窗断口、
端点不对齐，投入大而失败率高。走另一条路：体检先告诉画图的人改哪几处（12 项里通常只
差两三条），改完工具就能读。**图纸不规范时不做费时的大模型推理**——先让图可读。

下一步要挑检测手段靠得住的条文补 `machine`：房间面积、疏散距离、楼梯净宽这些能从
房间边界和楼梯段算出来；「经常有人停留」「可燃物较多」这类定性判断不碰。
`cadspec kb coverage` 会一直显示这个比例，不让它悄悄变成一句空话。

## 两条腿，速度不一样

|  | 条文 Clause | 规则 Rule |
|---|---|---|
| 面向谁 | agent 检索、人查 | 自动校验 |
| 数量级 | 37 本 × 数十至数百条 | 每一条都要设计检测方法 |
| 推进方式 | 可批量：抓取 → 结构化 → 复核 | 逐条：先想清楚怎么判，再写 |

**先把条文库做厚，规则慢慢长。** 规则数量不需要跟上条文数量 —— 一个条文库有一千条、规则只有五十条，是正常状态；反过来才奇怪。

绝大多数条文天然只能检索不能自动判（"楼梯间应能天然采光和自然通风"怎么从 DXF 里判？），强行为它们写规则只会产出假阳性。

## 每条条文录什么

```yaml
- clause_id: GB55037-2022/7.1.1
  verbatim: |            # 原文。用「应/宜/不应」原字，不改写
  interpret: |           # 转述成人话，补上下文
  severity_hint: error   # 由用词定：应/不应/必须/不得 → error；宜/不宜 → warning
  machine:               # 可选。能被程序执行的约束才写
    min_value: 1100
    unit: mm
  status: effective
  source_url: ...
  source_note: |         # 版本、核对过程、为什么这样定级
```

**`machine` 不是每条都有。** 没有就别硬写 —— 写了但用不上的 `machine` 块，会让后面写规则的人以为有据可依。

## 测试策略

- **合成图**：用 `ezdxf` 在测试里现场造。一个测试精确对应一条规则，不依赖外部文件。这是主力。
- **`1.dxf`**：回归基线。防止改代码时把已经通过的规则打回原形。
- **真实图纸不作为路线图来源**。一张图暴露的是它自己的缺漏，不是规范库的覆盖面。规则该覆盖什么，由条文决定。

## 闭环验证暴露的三个几何 bug（已修）

第一次完整跑「体检 → 审查 → 补图 → 再审查」时，补完三处图之后房间数从 11 掉到 9。
查下来不是图的问题，是几何模块自己有三处错：

1. **门扇弧没参与围合**。`_door_arcs()` 认出的门只进了 `openings` 列表用于报告，
   它的开口线没进 `bridged`。房间能否闭合全靠 `_bridge_gaps` 兜底补线，
   一旦缺口超过 `GAP_MAX` 就兜不住，那个房间和隔壁合并成一个。
2. **弧端点没跟墙线一起吸附**。墙端点被 `_snap` 聚类平均过，弧用的是原始坐标，
   两边差零点几毫米。现在弧与墙线一起进 `all_segs`，统一 `_snap` 后再切片。
3. **量化网格太细**。`polygonize` 用精确相等判环闭合，而 `_snap` 的平均会让
   同一个交点在不同线上差 0.01~0.02mm —— `GRID_MM = 0.01` 正好卡在这个误差量级上，
   量化后仍差一格。改成 **1.0mm**（远小于建筑精度，182.09m² 的房间只差 0.01m²）。

修完后 `1.dxf` 与三张补图出来的房间数一致（都是 11 间），总面积一致。
顺带发现：原实现把 `1.dxf` 的两个独立房间算成 11 间里的一个，
是这次修 `GRID_MM` 才显出来的 —— 先前外部审查说「工具漏检两个房间」，
其中一个是对的。

**教训**：几何 bug 不会在单张图上暴露。补图前后房间数的变化，是最灵敏的探针。

## 不做什么

- 不收录国家建筑标准设计图集（22G101 等）的任何图片、截图、PDF。该系列著作权归中国建筑标准设计研究院，公开声明未授权以图集内容制作电子文件传播。详见 `data/LICENSE`。
- 不为了让某张图的报告变绿而加规则。
- 不在识别方法不可靠时上规则（剖切符号、指北针、防火分区都属于这一类，条文先录，规则等检测手段成熟）。

## 贡献指引

想加一个标准：

1. 在 `data/kb/` 建 `<standard-id>.yaml`，按上面的格式录条文；
2. 在 `data/rules/` 建同名文件，写能自动判的规则，每条 `cite` 指回条文；
3. `cadspec kb verify` 会校验 `cite` 是否存在 —— 指向不存在的条文会直接报错；
4. 在 `tests/test_rules.py` 加用例，用合成图造；
5. 跑 `pytest` 和 `cadspec check 1.dxf`，确认没把已有的规则打坏。
