# 让 agent 用 cadspec 画合规的图

这份文档定的是下一阶段的开发策略。目标不是把条文库补到三千条，而是让一个
agent 在画图的过程中真的会来问 cadspec，并且问得到答案。

条文缺口（626 / 约 3600）留到后面慢慢补，它不阻塞这条链路。

---

## 一、先说清楚"用规范画图"是什么意思

agent 画 CAD 有四个时机可能用到规范库，cadspec 目前只覆盖了最后两个里的一半：

| 时机 | agent 的问题 | cadspec 现在能不能答 |
|---|---|---|
| 画之前 | 「住宅厨房最小使用面积是多少」 | ❌ 只能按条号查，agent 不知道条号 |
| 画的时候 | 「这个卧室的门洞该留多宽」 | ❌ `machine` 只有 20 条有内容 |
| 画完自检 | 「这张图哪里不合规」 | ✅ `check` 可用 |
| 改完复检 | 「改完还有问题吗」 | ✅ 同上，但要人手动触发 |

所以现在的产品形态是"事后审图工具"，不是"画图时的规范助手"。
这一阶段的全部工作，就是把它变成后者。

---

## 二、三层接口，缺两层

```
L1 检索层   ask       「这条规范怎么说」       ← 要新建
L2 约束层   constrain 「这个参数该取多少」      ← 要新建，依赖 machine 填充
L3 检查层   check     「这张图画得对不对」      ← 已有
```

**为什么必须先做 L1 和 L2，而不是继续堆 L3 的规则**

`check` 的定位是"挑错"，但 agent 画图时最缺的不是被挑错，是**画之前不知道该画多少**。
一个 agent 画了 700 的门洞，你事后告诉它"要 900"，它得返工；它画之前问一句，
就省了这趟。而且 L3 每加一条规则都要设计检测方法（几何识别），L2 只是把
已有的 `interpret` 整理成参数，成本差一个量级。

**结论：这一阶段的优先级是 L1 > L2 > L3。L3 不新增规则。**

---

## 三、L1：检索层

### 接口

```bash
cadspec ask "住宅厨房最小使用面积" --format json
cadspec ask "厨房" --standard GB55038-2025 --limit 5
```

输出：

```json
[
  {
    "clause_id": "GB55038-2025/4.1.4",
    "standard": "GB55038-2025",
    "section": "4.1 套内空间",
    "verbatim": "厨房的使用面积不应小于3.5㎡。",
    "interpret": "这是净使用面积，不是轴线面积……",
    "machine": { "subject": "kitchen", "min_area_m2": 3.5 },
    "severity": "error",
    "score": 0.82
  }
]
```

### 实现

不引入向量检索。理由：零依赖是这个项目的底线，而且 626 条条文的关键词已经在
ingest 阶段抽出来了（`keywords` 字段，含数值锚点如 `3.5㎡`、`1800mm`）。

打分用三路加权：

1. **关键词命中**：查询词与 `keywords` 的交集，按 IDF 加权（越少见的词权重越高）
2. **原文命中**：查询词直接出现在 `verbatim` 里的额外加分
3. **标准/章节过滤**：`--standard`、`--section` 是硬过滤

再加一个**同义词表**（`data/synonyms.yaml`），处理"厨房间/厨房/灶间"、
"起居室/客厅"这种叫法差异。这张表是手写的，几十条就够。

### 验收

- 「住宅厨房最小使用面积」→ 第 1 条必须是 `GB55038-2025/4.1.4`
- 「楼梯踏步宽度」→ 命中 `GB55031-2022/5.3.9` 且带出附表
- 「无障碍坡道坡度」→ 命中 GB 55019 相关条
- 十条手写查询里至少中八条

## 四、L2：约束层

### 前提：先填 machine

现在 626 条里只有 20 条有 `machine` 内容。这一阶段的目标不是填满，是**挑出
画图时真会用到的 40~60 条**，把它们填成结构化约束。

挑选标准（三条同时满足才填）：

1. 这条约束有明确数值或枚举（不是"应合理设置"）
2. 这个数值由画图的人决定（不是消防设备选型那种）
3. 数值能对应到图纸上的某个量（面积、宽度、高度、数量）

按这个标准，优先填：

- GB 55038 第 4 章：房间面积、净高、门洞宽、过道宽、楼梯踏步、栏杆高度
- GB 55031 第 5 章：楼梯、走廊、台阶、电梯、卫生间
- GB 55019：坡道坡度、门宽、扶手高度、回转空间
- GB 55037 第 7 章：疏散净宽、出口数量（这几个偏计算，标 `partial`）

### 接口

```bash
cadspec constrain --subject 卧室 --format json
cadspec constrain --subject 厨房 --field min_area_m2
```

输出：

```json
{
  "subject": "卧室",
  "constraints": [
    { "field": "min_area_m2", "value": 5.0, "clause": "GB55038-2025/4.1.1", "unit": "m²" },
    { "field": "min_short_side_mm", "value": 1800, "clause": "GB55038-2025/4.1.1", "unit": "mm" }
  ],
  "ambiguous": ["兼起居室的卧室要求 9m²，取决于房间用途，见 4.1.1"]
}
```

`ambiguous` 这个字段是刻意留的：有些条文的取值取决于前提（比如这间是卧室还是
起居室），接口不能假装知道，要把分歧列出来让 agent 自己判断或者反问人。

### 验收

- agent 输入「我要画一个 8m² 的卧室」，`constrain --subject 卧室` 能返回面积和短边两条
- 输入不存在的 subject，返回空数组和一句"没有匹配的约束"，不瞎猜

## 五、L3：检查层（只修不加）

不新增规则。只做两件事：

1. **让 `check` 的输出对 agent 更友好**：`findings` 里每条加 `fix_hint`
   （人话建议，比如"把门洞从 700 改到 900 以上"），但**不生成具体改图操作**——
   改图是 pilot 的事。
2. **补 `--baseline` 参数**：存一份上次的结果，只报"新增的问题"。这样
   agent 改完一轮再跑，能看到自己有没有改坏别的地方。

## 六、给 agent 的接入方式

### DSH 侧：一个小插件，两个 tool

```
cadspec.ask       → cadspec ask <query> --format json
cadspec.check     → cadspec check <dxf> --scale N --level strict --format json -o <tmp>
```

不写 MCP（理由见 `docs/design.md` 第 12 节：这是无状态纯函数，不需要长连接）。
插件内用 `child_process.spawn`，读 `-o` 写出的文件——**不要用管道**，PowerShell 会给
JSON 加 BOM。

### skill 侧：写清楚"什么时候该问"

现有的 `skills/cadspec/SKILL.md` 只讲了怎么用，没讲**什么时候用**。要补一节：

- 开始画一个房间之前：先 `ask` 这个房间的面积/短边/层高要求
- 画门窗之前：先 `constrain` 门洞宽度、开启方向
- 画楼梯之前：先 `ask` 踏步尺寸、梯段净宽
- 画完：`check`，把 error 逐条修掉再交
- 改完：再 `check` 一次，确认没有引入新问题

这段是这一阶段最容易失败的地方：agent 不会主动查，除非你告诉它"画之前先问"。

## 七、里程碑

| 阶段 | 内容 | 工作量 | 完成标志 |
|---|---|---|---|
| M1 | `ask` 检索接口 + 同义词表 | 1~2 天 | 十条手写查询中八条 |
| M2 | 填 40~60 条 `machine` | 3~4 天 | 覆盖四个高频房间/构件 |
| M3 | `constrain` 接口 | 1~2 天 | 按 subject 能取出约束 |
| M4 | DSH 插件（两个 tool）+ skill 补"何时问" | 1~2 天 | 插件里能跑通 ask 和 check |
| M5 | 端到端：agent 从零画一张图 | 2~3 天 | 见下方验收 |

M1 和 M2 可以并行——一个动手写检索，一个动手填数据。

## 八、端到端验收

让人给 agent 一句话：「画一张 60m² 的两居室住宅平面，要有厨房、卫生间、两个卧室」。

合格标准，按重要性排序：

1. **agent 在动手之前调用过 `ask` 或 `constrain`**，而不是画完才查
2. 画出来的图 `check` 后 **error 为 0**，warning 里没有"尺寸不足"类
3. **人没有告诉过它任何具体数字**（门宽、面积、层高都来自 cadspec）
4. 单次 `check` 在 10 秒内
5. agent 能解释每条结论的依据条号

第 1 条和第 3 条是这一阶段真正的成败点。第 2 条只要前面几层做对了是自然结果。

---

## 九、明确不做

- **不做向量检索 / embedding**：零依赖是底线，关键词加同义词够用
- **不做双线墙识别**：那是通用 CAD 解析器的活（见 `docs/roadmap.md`）
- **不做图形生成**：agent 自己画，cadspec 只提供规范和判定
- **不继续堆检查规则**：到硬指标为止，理由见 `docs/design.md` 第 6 节
- **不做网页版**：现在没有服务器，也不该为一个离线工具引入服务器

## 十、已知风险

| 风险 | 影响 | 应对 |
|---|---|---|
| agent 不主动查 | 整套接口形同虚设 | skill 里写死触发条件；验收第 1 条专门测这个 |
| `machine` 填得不够 | `constrain` 返回空 | M2 优先填四个高频构件：卧室、厨房、卫生间、楼梯 |
| 条文语义对不上图纸实体 | 「疏散距离」这类需要房间边界和门位置，几何层给不全 | 这类条文标 `partial`，`constrain` 明确写"需要额外信息" |
| 检索不准 | agent 问不到、问错 | 十条手写查询做回归测试，进 CI |
| agent 把 `宜` 当 `应` | 判得过严，把图改坏 | `severity` 已在数据层区分，`ask` 输出里要带上 |
